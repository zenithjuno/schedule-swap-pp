STAGE 23 — Self-export "สร้างไฟล์พร้อมใช้ (.html)"

  What it does:
    - New button in ตั้งค่า → data-management bar: "สร้างไฟล์พร้อมใช้ (.html)".
    - Serializes the running document into a fresh single .html whose embedded-
      data island is filled with the ACTIVE semester's schedule + the program
      phone book + settings — and deliberately NOT the Log.
    - Filename: ระบบสลับคาบ_{label}_พร้อมใช้.html
    - Restore-state line confirms "✓ สร้างไฟล์พร้อมใช้แล้ว (ไม่รวม Log)".

  How it works (technical):
    - buildReadyFileHTML(): builds the payload {semester:{label,start,end,
      sourceFilename,rows}, phones, settings}, serialises with the lean replacer
      (rows carry NO derived fields — the child re-derives on load), escapes the
      one HTML-breaking sequence "</script" -> "<\/script" (JSON-safe; restored on
      parse), sets the embedded-data island's textContent, captures
      '<!DOCTYPE html>\n' + document.documentElement.outerHTML, then RESTORES the
      live page's island + body class so the running page is unchanged.
    - exportReadyFile(): wraps that in a Blob download.
    - Load precedence (already present from earlier stages): the browser store
      wins if it already has an active semester; the embedded island only seeds an
      empty store; a prior "ล้างทั้งหมด" (noEmbed) still suppresses it.
    - The export carries the lean schedule (~0.9 MB) so the child stays small.

  Acceptance — three-generation reproduction (the plan's hard loop), headless
  jsdom, each generation on a CLEAN origin:
    - gen0 (master) boots embedded semester; a Log row is added to prove it is
      NOT exported; an adversarial value "X</script>Y<!--Z-->W" is injected into a
      row.
    - gen1 (child): no boot errors; loaded embedded data; FULL self-test GREEN
      21/21; Log ABSENT; phones present; 3823 rows; "</script>" + "<!--" survived
      byte-exact; leading-zero teacher_id preserved; Thai (จันทร์) intact.
    - gen1 re-exports -> gen2 (grandchild): no boot errors; self-test GREEN; data
      present + Log still absent; "</script>" survived 3 generations; Thai
      byte-exact across all three (teacher_name compared gen1 vs gen2).
    - Result: 19/19. No data corruption, no encoding loss, three generations deep.

  Regression: s22a 22/22, s22 features 30/30, lean storage 10/10, engine 21/21.

  TESTING CAVEAT for manual verification on this machine (Safari):
    - Safari shares localStorage across ALL file:// pages, so opening the exported

      data is (correctly) ignored. To see the true cold-open colleague experience,

FIX — lean localStorage (schedules persisted without derived fields)

  Symptom (user-reported, with screenshot):
    Importing a 2nd full semester (3,823 rows) failed with
    "บันทึกไม่สำเร็จ: พื้นที่จัดเก็บในเครื่องเต็ม". Archiving itself was fine —
    it is automatic on import (the active semester auto-archives, the new one
    becomes active) — the SAVE is what overflowed.

  Root cause:
    Each schedule row was persisted WITH ~10 derived fields (level, lunch_period,
    is_lunch, is_combined, nt_class, is_teaching, is_eligible, building, key_tdp,
    key_gdp). That made one semester ~1.67 MB and two ~3.33 MB. On file://,
    localStorage is accounted in UTF-16 (≈2 bytes/char) and Thai text is
    multi-byte, so the effective footprint crossed the browser's ~5 MB ceiling at
    the second full semester.

  Fix (in-memory model and engine UNCHANGED; only the persisted form changes):
    - STORE.save() now serialises with a replacer (leanReplacer) that omits the
      10 derived fields. Persisted rows keep only raw fields
      (teacher_id, teacher_name, day, period, subject, group, room, raw_cell,
      status, audit_note).
    - On load, the existing boot pass already re-derives any semester lacking
      derived flags (ensureSemesterDerived → deriveRows). Lean rows are therefore
      re-hydrated in memory before the engine ever uses them.
    - The boot pass now re-persists once on every open (was: only if it had to
